# アートワークの推奨仕様

kotone はアルバムアートを**クロップせず、原盤の比率のまま**表示します
（要件定義書 3.3）。ここでは、自分でアートワークを用意するときの推奨仕様を示します。

## 推奨仕様

| 項目 | 推奨 |
|---|---|
| 形式 | **PNG**（可逆） |
| 解像度 | **短辺 1400px 以上** |
| 比率 | 原盤どおり（正方形である必要はありません） |
| 色空間 | sRGB |
| 埋め込み先 | 音源ファイルへの埋め込み（FLAC の PICTURE ブロック等） |

短辺 1400px で用意すれば、最大のキャッシュ階層をほぼそのまま使えます。

## キャッシュの仕組み

スキャン時に、**短辺**を基準として 3 階層の PNG を事前生成します。
配信時のリサイズは行いません（要件 4.6）。

| 階層 | 短辺 | 用途 |
|---|---|---|
| 小 (small) | 300px | 一覧のサムネイル |
| 中 (medium) | 800px | スマートフォンの再生画面 |
| 大 (large) | 1400px | iPad / PC など大画面・高 DPI |

長辺は元の比率のまま拡大縮小されるため、たとえば 2000×1000 の横長アートは
小 600×300 / 中 1600×800 / 大 2000×1000 になります。

### 元画像が小さい場合

**拡大は一切行いません。** 元画像の短辺を超える階層は作らず、代わりに
その階層を元解像度のまま 1 度だけ生成します。

例: 短辺 500px の元画像
- 小 = 300px（縮小）
- 中 = 500px（元解像度のまま）
- 大 = 生成しない（中と同じ解像度になるため）

API が要求された階層を持っていない場合は、存在する中で最大の階層に
自動でフォールバックします。

### 変換について

- 元がどの形式でも、キャッシュは **PNG（可逆）に統一**します。
  リサイズ以外の劣化を足さないためです。
- 縮小には Pillow の **LANCZOS** を使います
  （要件の「バイキュービック法相当」を満たす上位互換）。
- JPEG の原盤を使う場合、JPEG 由来の劣化はそのまま残ります。
  可能なら PNG で用意してください。

## アートワークの探索順序

1. 音源ファイルに埋め込まれた画像（front cover を優先）
2. 同じフォルダの画像ファイル
   `cover.png` → `cover.jpg` → `folder.*` → `front.*` → `album.*` →
   （見つからなければフォルダ内で最大サイズの画像）
3. FFmpeg による埋め込み画像の抽出（mutagen が扱えない形式のフォールバック）

アルバムの先頭トラック（ディスク番号・トラック番号順）から取得します。

## キャッシュの再生成

アートワークを差し替えたときは、そのファイルのタイムスタンプが変わるため
通常のスキャンで自動的に再生成されます。

フォルダ内の画像だけを差し替えた場合は、音源ファイルが変わらないため
完全な再スキャンが必要です。

```bash
sudo -u kotone kotone-cli scan --full
```

キャッシュの実体は `/var/lib/kotone/artwork/<先頭2文字>/<ハッシュ>/` に
`small.png` / `medium.png` / `large.png` として置かれます。SQLite には
ファイルパスのみを記録し、画像バイナリは DB に入れません。
