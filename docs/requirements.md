## 0. 文書情報

- 作成日: 2026-08-07
- ステータス: v0.3(要件定義を区切り、Claude Code主導での初期実装フェーズへ移行。プロジェクト名のみ意図的に保留中)
- 想定実装者: Claude Code
- 本文書の位置づけ: 実装の土台となる要件整理。以降は実装しながら気づいた点を都度この文書または実装側にフィードバックしていく運用とする

## 1. プロジェクト概要

### 1.1 背景

- 従来はRaspberry Pi 4B上でmoOde OSを運用していたが、UI/UXへの不満からpiCorePlayer + Lyrion Music Server(LMS) + Material Skinの構成へ移行した経緯がある。
- 並行して、ChatGPT(GPT)と理想のプレイヤー像を検討し、moOde OSの上に自作のバックエンド・フロントエンドを重ねたプロトタイプを開発済み。`http://moode.local:8088` にPC/スマートフォンのブラウザからアクセスして操作する構成で、実際に動作している。
- しかし、このプロトタイプはmoOde OSへの依存が強く、「自力またはAIの助けを借りてRaspberry Pi環境を構築できる技術力のあるユーザー」でないと導入が難しいという課題が明らかになった。
- そこで、moOdeに依存しない自己完結型のプラットフォームとして再構築する方針に転換し、Claudeにも開発協力を依頼することとした。

### 1.2 目的

- Sony NW-ZX300のような軽快な操作感を持つ、フル日本語対応の音楽プレイヤーをRaspberry Pi上に実現する。
- ラズパイオーディオ向けで日本語ネイティブなプラットフォームは先行例が見当たらないため、新たな選択肢として提供する。

### 1.3 想定ユーザー

- 主用途: 開発者本人による自宅オーディオ環境での利用。
- 公開時の想定ユーザー層: 「Raspberry Pi経験者向け」で確定。Raspberry Piをオーディオ目的で導入する時点で、環境構築の大筋を理解していると考えられるため、完全な非技術者向けの導入体験までは目指さない。

## 2. システム構成概要

| 項目 | 方針 |
|---|---|
| 動作環境 | Raspberry Pi上で動くWebアプリ(ブラウザ操作、PC/スマホ両対応) |
| 対象ハードウェア | Raspberry Pi 4B以上(ファンレス運用が容易なPi4を基本推奨)。USB DACはUAC2(USB Audio Class 2.0)準拠機種全般での動作を目標とする。ドライバ不具合を持つ個別機種への対応は都度対応とし、事前の網羅的な検証は行わない |
| 基盤OS | 公式Raspberry Pi OS(Lite想定)。moOdeには依存しない |
| 導入方式 | スクリプト型インストーラ(OS導入済み環境に対し、1本のスクリプトで一式セットアップ) |
| 再生エンジン | MPD(Music Player Daemon)を採用。ALSA/USB DAC制御、gapless再生の基盤として活用 |

アーキテクチャは以下の3層構成を想定する。

1. **MPD** — 再生エンジン、ハードウェア(ALSA/USB DAC)制御
2. **独自バックエンド** — MPD制御、タグDBキャッシュ、アートワーク処理、API層(REST/WebSocket等)
3. **独自フロントエンド** — ブラウザで動作するWeb UI(NW-ZX300ライクなUI、フル日本語)

ネットワークは家庭内LANのみを前提とし、外部公開・クラウド連携は現時点でスコープ外とする。

## 3. 機能要件

### 3.1 再生機能

- gapless再生(トラック間に空白を生じさせない)
- トラック先頭の音切れ・欠落を発生させない再生開始処理
- MPDのcrossfade/gapless機構を活用しつつ、不足があれば独自バックエンド側で補完する
- リピート機能: 1曲のみのリピートに加え、アルバム内/プレイリスト内/全曲の範囲を指定したリピートに対応する。MPDの`repeat`/`single`フラグとキューへの読み込み範囲の組み合わせで実現する
- シャッフル機能(重複なし): アルバム内/プレイリスト内/全曲の範囲を指定したシャッフルに対応する。対象範囲の全曲を再生し終えるまで同じ曲が重複しない。MPDの`random`フラグで実現する
- ランダム機能(重複あり): シャッフルとは別に、対象範囲から毎回独立して次の曲を抽選する方式にも対応する(往年のWalkmanの「ランダム」機能を踏襲)。同じ曲が連続または短い間隔で再度選ばれる可能性がある。MPD標準機能にはないため、独自バックエンド側で再生終了を検知し、都度ランダムに次の曲を選んでキューに追加する形で実装する
- ラウドネス補正: 配信プラットフォームと同様に、曲ごとのラウドネス値を計測し、再生時の音量ギャップを補正する。ライブラリスキャン時にrsgain(EBU R128準拠)で計測し、補正値はSQLiteに保存する(元のFLACファイルへのタグ書き込みは行わない)。独自バックエンドが再生開始時にMPDへ動的に音量調整を指示する形で適用する
- クロスフェード(曲間フェード): MPDの`crossfade`設定を用いて実現する。ON/OFFと秒数をユーザーが設定できるようにし、既定値はOFFとする

### 3.2 ライブラリ管理

- 楽曲タグの管理(表示・編集)
- ソート機能。対応軸はアーティスト/アルバム/ジャンル/リリース年/ライブラリへの追加日順とする(アルバム内はトラック番号順が基本)
- アーティスト名・アルバム名の日本語(漢字混じり)表記は、文字コード順では正しい「あいうえお順」にならないため、読み仮名をソートキーとして別途保持する
- 読み仮名はライブラリスキャン時にfugashi + unidic-lite(MeCabベースの形態素解析)を用いて自動生成する。精度を優先し、pykakasi等の軽量ライブラリよりもこちらを採用する
- 自動生成した読みが誤っている場合に備え、既存の「楽曲タグの管理」機能の一部としてユーザーが読みを手動修正できるようにする
- 低圧縮・高画質のDBキャッシュ(タグ情報・アートワークを劣化少なく保持)
- タグDBキャッシュのDBエンジンはSQLiteを採用する。サーバープロセス不要でPythonに標準搭載されており、個人ライブラリ規模のソート・検索には十分な性能を持つため

### 3.3 アートワーク表示

- 非正方形のアルバムアートを、強制クロップせずそのまま表示する
- PNG/JPEGを画質劣化最小限で表示する
- バイキュービック法相当の高品質リサイズ処理を行う
- サムネイルはライブラリスキャン時(または初回アクセス時)に事前生成しキャッシュする。ブラウザからのリクエスト時にオンデマンドでリサイズ計算は行わない
- 一覧表示用の小サイズと再生画面用の大サイズなど、用途別に複数サイズのキャッシュを持つ
- キャッシュ画像はファイルシステム上に保存し、SQLiteのDBにはファイルパスのみを記録する(画像バイナリをDBに埋め込まない)
- キャッシュは用途別に3階層のサイズを持つ: 小(一覧サムネイル用、短辺300px)/中(スマホの再生画面用、短辺800px)/大(iPad・PC等の大画面・高DPI画面用、短辺1400px)
- 保存形式はPNG(可逆)に一本化する。ユーザーが用意する元アートワークの形式によらず、キャッシュ生成時にPNGへ変換する。リサイズ処理自体で新たな劣化を追加しないことを目的とする
- 元画像(埋め込みアートワーク)の実解像度を超える階層は生成しない。実解像度がキャッシュ階層の解像度を下回る場合は、生成可能な階層までにとどめる(拡大による画質劣化を避けるため)
- ユーザーが新たに用意する原盤アートワークについては、PNG形式・短辺1400pxを推奨仕様としてドキュメントに明記する(この解像度で用意すれば、最大キャッシュ階層をほぼそのまま使える)

### 3.4 プレイリスト管理(MVPスコープ)

- プレイリストはタグDBと同じSQLiteで管理する(MPD標準のm3uファイルには依存しない)。再生時にはプレイリストの収録曲をMPDのキューへ読み込んで再生する
- 標準的なm3u形式でのエクスポート/インポートに対応し、他ソフトとのデータ持ち出し・取り込みができるようにする
- 作成: 空のプレイリストを新規作成、または曲・アルバムを選択してから既存/新規プレイリストへ追加する、の2通りに対応する
- 編集: 曲の追加/削除/並び替え。操作のたびに自動保存し、明示的な保存操作は設けない
- 再生: プレイリストの「再生」操作で収録曲を先頭からMPDキューに読み込んで再生開始する。個別の曲を選択した場合はその曲から再生開始する

### 3.5 UI/UX

- 画面遷移は基本的にタップ操作(常時表示のタブバー、ボタン、リスト項目のタップ等)で完結させる。PCブラウザのマウス操作でも同じ導線で操作できることを必須とする
- ZX300のような上下左右スワイプによる画面呼び出しの再現は行わない。ブラウザ環境ではOS/ブラウザ標準のジェスチャー(戻る操作、プルリフレッシュ等)と衝突するため
- 曲送り/曲戻し等、補助的なジェスチャーを設ける場合は、画面端(エッジ)からではなく操作対象の内部(アルバムアート上の横スワイプ等)に限定する
- フル日本語UI

### 3.6 ダイレクトサーチ(横断的な曲探索)

- 再生中画面に表示されるアーティスト/アルバム/年/ジャンルの各項目をタップすることで、その値を軸にライブラリ全体を横断的に絞り込める(ソニーのかつての「ダイレクトサーチ」機能を踏襲)
- アーティストを選択した場合、そのアーティストを含む全曲一覧("All○○")と、それらの曲が収録されているアルバム一覧を表示する
- 一覧から曲を選択するとその曲が収録されるアルバムに遷移し、再生を開始する。この遷移は繰り返し辿ることができ(曲→アーティスト→別の曲→別のアーティスト...)、「戻る」操作で遷移履歴を遡れるようにする
- 年・ジャンルでの絞り込みは値の完全一致によるシンプルなフィルタとする
- データモデル: アーティストは独立したエンティティとして正規化し、曲とアーティストを多対多で関連付ける中間テーブルを持つ(3.2節の読み仮名正規化と共通の基盤を使う)
- 現在のタグ付けでは1つのARTISTフィールドに区切り文字で複数アーティスト名が並記されているため、ライブラリスキャン時に区切り文字で分割してアーティストエンティティを生成する。具体的な区切り文字は実装時に実際のタグデータを確認して判定する。自動分割の誤り(区切り文字がアーティスト名自体に含まれる場合など)に備え、既存の「楽曲タグの管理」機能の一部として、曲ごとのアーティスト紐付けを手動修正できるようにする

### 3.7 イニシャルサーチ

- 「カナ」「英数・他」のタブと、50音/英数字のグリッドから頭文字を選択することで、アルバム一覧等の長いリストを頭出しできる(ソニーのかつての「イニシャルサーチ」機能を踏襲)。3.2節の読み仮名データをそのまま利用し、新たなバックエンド処理はほぼ不要
- 「英数・他」タブでは、ラテン文字表記のアーティスト・アルバム名を変換不要のソートキーとしてそのまま扱う
- タッチ操作に配慮し、常時画面の隅に表示するのではなく、専用ボタンから全画面オーバーレイとして開く形にする。タップ領域は一定サイズ以上(目安1タップ領域あたり44px四方程度)を確保する
- 画面サイズに応じて、大画面(PC/iPad等)ではグリッド表示、小画面(スマホ)では縦一列のインデックス帯(あ・か・さ・た・な…をなぞって選ぶ方式)への切り替えを検討する

## 4. 非機能要件

### 4.1 対応ライブラリ形式

- CDリッピング由来のFLAC(44.1kHz/16bit)を主とし、24bit/192kHzのFLACにも対応する
- DSD形式にも対応する
- MP3等の非可逆フォーマットにも対応する
- 対応フォーマットを積極的に限定する理由はないため、MPDが標準で扱える主要フォーマットは広く対応する方針とする

### 4.2 信頼性・安定性

- 静音・安定動作を優先する(既存運用方針を踏襲)
- ストレージはSSD/USBメディアを想定する

### 4.3 ネットワーク・セキュリティ

- 家庭内LAN限定での利用を前提とし、外部への公開は行わない
- クラウド連携は現時点でスコープ外

### 4.4 保守性

- 交換可能な部品構成、トラブルシューティングしやすい設計を志向する(既存運用方針を踏襲)

### 4.5 国際化

- UIはフル日本語対応を必須とする

### 4.6 操作レスポンスの快適性

- 一覧のスクロール、曲切り替えなど主要な操作は体感的な遅延なく反応すること
- アルバムアートはキャッシュ済みサムネイルを返却するのみとし、リクエストのたびにリサイズ計算を行わない(詳細は3.3参照)
- フロントエンドは画面内に入った画像から読み込む遅延読み込み(lazy loading)を行う

### 4.7 実装言語・技術スタック

- バックエンドはPythonで実装する。画像処理(Pillow)やMPD操作ライブラリ(python-mpd2)のエコシステムが充実していることを理由に選定
- バックエンドのWebフレームワークはFastAPIを採用する。ASGIベースでWebSocketを標準で扱え、型ヒントからAPIドキュメント(Swagger UI)が自動生成される点を理由に選定
- 日本語の読み仮名自動生成にはfugashi + unidic-lite(MeCabベースの形態素解析)を使用する
- フロントエンドはSvelte等の軽量フレームワークを採用する。保守性(画面・状態をコンポーネント単位で管理できる)とビルド後の軽さ(操作レスポンスの快適性)の両立を理由に選定。ビルドは開発時(Claude Code側)で行い、インストーラはビルド済みの静的ファイル(HTML/CSS/JS)を配置するのみとし、Pi上にNode.js等のビルド環境は不要とする

## 5. インストーラ要件

- 配布形態: スクリプト型(例: 1本のセットアップスクリプトを実行する形式)
- 前提条件: 公式Raspberry Pi OS(Lite)が書き込み・起動済みであること
- スクリプト実行により、MPD・独自バックエンド・独自フロントエンド一式が自動セットアップされること
- アプリ本体はGitHubリポジトリを`git clone`する形で導入する。フロントエンドはビルド済み静的ファイルをリポジトリに含めておき、Pi上でのビルドは不要とする
- 更新は`git pull`ベースの手動アップデート機構とする(自動更新は行わない)。ユーザーが明示的にアップデートコマンドを実行したときのみ更新される
- 楽曲DB(SQLite)、キャッシュ済みアートワーク、設定ファイル等のユーザーデータはgit管理下の外側に置き、アップデートで上書きされないようにする
- DBスキーマが変更された場合に備え、バージョン管理された移行スクリプトを用意し、アップデート時に必要な分だけ順次適用する
- 詳細(対応OSバージョン、必要な依存パッケージ、エラー時のリカバリ手順など)は今後詳細化する

## 6. スコープ外・将来拡張

以下は初期バージョン(MVP)には含めず、必要に応じて将来拡張として検討する。

- DLNA/AirPlay/Chromecast等の外部連携
- 複数Pi/マルチルーム対応
- スマホ向けネイティブアプリ化(ZX300ライクなジェスチャー操作、OSメディアセッション連携等)。現時点では、iOS App Store配信を個人で継続する際の資金繰り(広告・シェアウェア化等)がユーザー体験を損ねると考えられるため保留
- EQ/トーンコントロール。DACアンプ本体側の機能で代替可能なことと、Linux上でのDSP実装(ALSAレベルでの挿入、サンプルレート変換やgapless再生との整合性検証等)のコストが大きいため、MVPからは除外する
- 歌詞表示。過去の自作経験でユーザー層が広がらなかった経緯があり、優先度を上げる強い理由がないため見送る。再挑戦する場合はLRC形式(タイムスタンプ付き歌詞の標準フォーマット)を土台にする

## 7. 制約条件

- 開発・保守はAI支援(主にClaude Code)を前提とする
- GitHubでの公開を検討中。ライセンスはMIT Licenseを採用する。第三者が本プロジェクトを元に有料製品を作ることも許容する方針で、コピーレフト(GPL等)による囲い込み防止は重視しない
- GPT製プロトタイプ(kotone-pi-v0.3.2、Python製、Debian 13 aarch64/Python 3.13。追加パッケージ・Node.js・DB不要のステートレス設計)は、moOde依存部分とDBレス設計そのものは今回の方針と異なるため対象外とする。一方で以下は実装時の参照・流用候補とする
  - アートワーク取得の多段フォールバック(MPDのreadpicture→albumart→取得不可時はFFmpegでSSD上の音源から埋め込み画像を直接抽出)
  - MPD基本操作(再生/一時停止/前後移動/シーク/音量)のラッパーロジック
  - `object-fit: contain`相当による非正方形アートワークの縦横比維持
  - systemdサービス化の構成(install.sh/uninstall.sh、systemctlでの起動/停止/状態確認、journalctlでのログ確認)
- DB設計・API設計・ソート機能・フロントエンドは今回の新方針(SQLite、複数軸ソート、Svelte等)に合わせて作り直す
