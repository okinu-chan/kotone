## 1. 再生モデル：スコープ（再生範囲）という概念

要件 3.1 のリピート / シャッフル / ランダムはいずれも「対象範囲」を持つ。
そこでバックエンドに **再生スコープ (PlayScope)** を導入した。

```
PlayScope = { kind: "album" | "playlist" | "artist" | "genre" | "year" | "all",
              id: <対象の識別子 or null> }
```

再生開始時、スコープに属する全曲を解決して MPD キューへ読み込む。
各モードは以下のように MPD フラグへマップされる。

| KOTONE のモード | MPD `repeat` | MPD `single` | MPD `random` | バックエンドの介入 |
|---|---|---|---|---|
| リピート: オフ | 0 | 0 | - | なし |
| リピート: 1曲 | 1 | 1 | - | なし |
| リピート: 範囲 | 1 | 0 | - | なし |
| シャッフル（重複なし） | 現在値 | 0 | 1 | なし（MPD の random がキュー内で重複しないため要件を満たす） |
| ランダム（重複あり） | 0 | 0 | 0 | **あり** — 下記参照 |

### ランダム（重複あり）の実装

MPD の `random` はキューを走査しきるまで重複しないため、Walkman の「ランダム」
（毎回独立に抽選）とは異なる。そこで独自実装する。

- キューは常に **`[再生中, 次の1曲]`** の 2 エントリだけを保つ。
- MPD の `idle player` で曲の切り替わりを検知したら、消費済みエントリを削除し、
  スコープから新たに 1 曲抽選してキュー末尾へ追加する。
- 次曲を「あらかじめキューに入れておく」のが要点で、これにより MPD の
  gapless 機構がそのまま効く（要件 3.1 の先頭欠落対策）。
- 直前 N 曲（既定 1 曲、設定可）を抽選対象から除外することで、
  「同じ曲が 2 回続く」極端なケースだけは避ける。完全独立抽選を望む場合は
  設定で `random_avoid_last` を 0 にできる。

実装: `kotone/playback.py` の `RandomModeDriver`。

## 2. ラウドネス補正の適用方法

要件 3.1 は「元 FLAC へのタグ書き込みを行わず、再生開始時に MPD へ動的に音量調整を
指示する」と定めている。MPD 内蔵の ReplayGain 機能はファイル側のタグを読むため使えない。

したがって次のようにした。

- **計測**: ライブラリスキャン時に `rsgain custom -s i` を実行し、EBU R128 準拠の
  track gain / peak / album gain / peak を取得して SQLite に保存する
  （`tracks.track_gain_db` ほか）。`rsgain` が未インストールでもスキャン自体は成功し、
  補正だけが無効になる。
- **適用**: バックエンドは「ユーザーが設定した音量 (`user_volume`)」を状態として保持し、
  曲が変わるたびに

  ```
  実効音量 = user_volume × 10^((gain_db + preamp_db) / 20)
  ```

  を計算して MPD の `setvol` に渡す。UI にはあくまで `user_volume` を表示する。

### 計測の所要時間（Raspberry Pi 4B 実測）

3 分の FLAC 1 曲あたりの計測速度（実時間比。大きいほど速い）:

| 方式 | 実時間比 |
|---|---|
| `loudnorm`（初期実装） | 9.1x |
| `ebur128 peak=true` | 21.7x |
| **`ebur128 peak=sample`（採用）** | **31.0x** |
| `ebur128`（ピーク計測なし） | 45.8x |
| デコードのみ（理論上限） | 171.3x |

並列数を変えた場合の合計スループット（`peak=sample`）:

| 並列数 | 合計 | 18,000 曲の所要時間 |
|---|---|---|
| 1 | 30.9x | 34.5 時間 |
| **2** | **49.9x** | **21.4 時間** |
| 3 | 51.7x | 20.6 時間 |
| 4 | 51.3x | 20.8 時間 |

**コア数ぶんスケールしない。** Pi 4B ではメモリ帯域が先に飽和するため、
2 並列で頭打ちの 97% に達する（CPU 温度は 59℃ 程度でサーマルスロットリングは
発生していない）。既定の並列数を 3 で打ち切っているのはこのため。
残りのコアは再生と UI のために空けておく。

この規模では計測は一晩で終わらないため、以下で運用上の負担を下げている。

- **中断・再開できる**: 計測済み（`gain_scanned_at` が入っている）曲は
  再スキャンでも測り直さない。途中で止めて翌日続けてよい。
- **タグを優先する**: ファイルに ReplayGain / R128 タグがあれば計測せずに使う。
  他のツールで一括計測済みのライブラリなら、計測時間はゼロになる。
- **計測中も再生できる**: 計測はバックグラウンドで走る。

さらに速くしたい場合は `rsgain`（libebur128 を直接使う専用ツール）を
`install.sh --with-rsgain` で導入する。FFmpeg のフィルタグラフを経由しないぶん
有利だが、本プロジェクトでは未計測。

### 前提と注意

- `setvol` による補正は **ソフトウェアミキサー前提**。インストーラは `mpd.conf` に
  `mixer_type "software"` を設定する。ハードウェアミキサー（DAC 内蔵ボリューム）を
  使う場合、補正は DAC のカーブ次第で不正確になるため、設定画面で補正を
  OFF にすることを推奨する。
- MPD の音量は 0–100 の整数のため、補正の分解能は約 1% 刻みに丸められる。
- 正のゲイン（音量を上げる方向）はクリッピングを招くため、既定では
  `clip_prevention` により `track_peak` を考慮して上限を制限する。
- MPD 側から音量が変更された場合（他クライアント等）と自分が設定した値を
  区別するため、`PlaybackController` は最後に自分が書き込んだ値を記憶し、
  `idle mixer` イベントがそれと一致する場合はユーザー操作として扱わない。

実装: `kotone/playback.py` の `LoudnessCompensator`。

## 3. 読み仮名とソートキー

要件 3.2 / 3.7 の基盤。`fugashi` + `unidic-lite` を使う。

### 生成

1. 文字列を NFKC 正規化（全角英数 → 半角、半角カナ → 全角カナ）。
2. `fugashi.Tagger` で形態素解析し、各語の `kana` / `pron` 素性を連結して
   カタカナ読みを得る。素性が取れない語（未知語・ラテン文字）はそのまま残す。
3. 読みが取れなかった、または元文字列がラテン文字のみの場合は
   **変換せず元の文字列をソートキーとして扱う**（要件 3.7）。

### ソートキー

読み文字列をそのまま比較すると濁音・小書き文字・長音記号で直感に反する順序になる。
そこで比較専用の正規化を行う（`kotone/text/sortkey.py`）。

- カタカナ → ひらがなへ統一
- 小書き文字（ぁぃぅぇぉっゃゅょゎ）→ 大文字へ
- 濁点・半濁点を除去（が→か、ぱ→は）
- 長音記号「ー」は直前の母音へ展開（コーヒー → こおひい）
- ラテン文字は小文字化

ただし正規化だけでは「か」と「が」が同順になるため、
**`(正規化キー, 原文読み)` の 2 段タプル**で比較する（SQLite 上では
`sort_key` と `reading` の 2 カラムを ORDER BY に並べる）。これで
「か → が → き」という辞書式の期待順序になる。

### イニシャル（頭文字）

`sort_key` の先頭文字から `あ/か/さ/た/な/は/ま/や/ら/わ` の行、
`A`–`Z`、`#`（数字・記号）のいずれかを求め、`initial` カラムに保存する。
イニシャルサーチはこのカラムへのインデックス検索だけで完結する。

### 手動修正の保持

自動生成の誤りをユーザーが直せる（要件 3.2）。修正時は該当行の
`reading_locked = 1` を立て、以降の再スキャンでは自動生成値で上書きしない。

## 4. アーティストの分割

要件 3.6 の通り、1 つの ARTIST フィールドに複数名が並記されている。

- **Vorbis Comment (FLAC/Ogg) の複数値フィールドを最優先で扱う。** mutagen は
  同名タグを list で返すため、区切り文字に頼らず正しく分割できるケースがある。
- 単一値だった場合のみ、設定された区切り文字リストで分割する。
  既定値は `[";", " / ", "／", "、"]` — カンマや `&` は
  アーティスト名自体に含まれる頻度が高いため既定では**含めない**。
- 実際のライブラリでどの区切り文字が使われているかを調べるため、
  `kotone-cli analyze-artists` を用意した。ライブラリを走査して区切り文字候補の
  出現頻度と該当例を表示する。**初回スキャン前にこれを実行し、
  設定 `artist_separators` を調整することを推奨する。**
- 分割結果が誤っていた曲は、タグ編集 UI から曲ごとにアーティスト紐付けを
  手動修正できる（`tracks.artists_locked = 1` が立ち、再スキャンで保持される）。

## 5. アートワークキャッシュ

要件 3.3。

- 取得の多段フォールバック（GPT プロトタイプの構成を踏襲）:
  1. 音源ファイルの埋め込み画像（mutagen）
  2. 同一ディレクトリの `cover.png` / `cover.jpg` / `folder.jpg` / `front.jpg` 等
  3. FFmpeg による埋め込み画像の抽出（mutagen が扱えない形式のフォールバック）
- リサイズは Pillow の `LANCZOS`。要件の「バイキュービック法相当」を満たす
  （LANCZOS は縮小品質でバイキュービックを上回るため、上位互換として採用）。
- **短辺**を基準に 300 / 800 / 1400 px の 3 階層を生成する。長辺は元比率のまま。
  これにより非正方形アートを一切クロップしない。
- 元画像の短辺を超える階層は生成しない（拡大による劣化回避）。生成できた最大階層が
  何かは `artwork_cache` テーブルに記録され、API はリクエストされた階層が
  無ければ**存在する最大階層**へフォールバックする。
- 保存形式は PNG 固定（`optimize=True`, `compress_level=6`）。
- 配信時はキャッシュファイルをそのまま返すだけ。オンデマンドのリサイズは行わない。
- ETag は元画像のハッシュ + 階層で生成し、`Cache-Control: public, max-age=31536000,
  immutable` を付ける（URL にハッシュを含めるため）。

## 6. DB マイグレーション

`backend/kotone/db/migrations/NNNN_*.sql` を番号順に適用する。適用済みバージョンは
`schema_version` テーブルに記録され、`kotone-cli migrate` および
バックエンド起動時に未適用分だけが順次実行される（要件 5 章）。

マイグレーションは**前方向のみ**。ロールバックが必要な場合は
アップデート前に取得される自動バックアップ（`/var/lib/kotone/backups/`）から戻す。
